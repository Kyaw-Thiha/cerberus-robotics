# RUN_002 — Rough candidate: reliability fixes + confirmed max-difficulty convergence (2026-09-08)

Follow-on to `RUN_001.md` (read that first for the full investigation history —
the stairs-rescale fix, the camera bug, the flat-spawn-zone reliability concern,
and the ~10hr monitoring-failure incident). This run doesn't re-derive any of
that reasoning; it's the run that acted on it: a fresh from-scratch Rough
retrain plus a fixed, wider eval sweep, run unattended end-to-end via a small
queued pipeline script so it didn't depend on any local terminal staying open.

## TL;DR

- **Confirms the stairs-rescale fix is reproducible**, not a one-off: a second,
  independent from-scratch retrain lands both stair types in the same range as
  the first fix run (`pyramid_stairs` 83.3%, `pyramid_stairs_inv` 66.4%).
- **Settles the "reaches highest difficulty" question with real per-env data**,
  not an inferred mean: added `Curriculum/terrain_level_max` /
  `Curriculum/terrain_level_frac_at_max` diagnostic logging (`core/curriculum.py`),
  confirming a real 11-16% of envs reach and cycle through terrain level 9
  through the back half of training.
- **Fixed a real eval measurement bug**: `push_recovery_eval.py`'s trials could
  get a "free win" from a lucky near-zero sampled velocity command, letting a
  robot "pass" without ever leaving its spawn point's flat terrain platform.
  Added a command floor (`--min_command_speed_mps`, default 0.5) plus
  displacement-from-spawn logging to prove it worked: 0.0% of 1800 trials, in
  every terrain type, showed under 1m of displacement.
- **Produced the missing "Done when" robustness-curve plot** —
  `policy/locomotion/eval/rough_push_recovery_curve.png` — the first time this
  artifact has actually been generated and saved, not just described.
- Training itself shows genuine convergence (terrain-level and fall-rate
  metrics both flatten well before iteration 1500) — more iterations at the
  same settings would not be expected to improve results further.
- `boxes` remains the checkpoint's weakest terrain type (63.6% pooled, 45% at
  the hardest level tested) — untouched by any fix this session, open question
  for later, not blocking.

## What was done

1. **Code changes going into this run** (see `RUN_001.md`'s recommendations
   and this session's own discussion for the reasoning):
   - `core/curriculum.py` / `core/go2_rough_env_cfg.py`: two new diagnostic
     `CurriculumTermCfg` terms, `terrain_level_max` and
     `terrain_level_frac_at_max` — read-only, no effect on training, just
     surfaces the per-env curriculum distribution that the stock mean can't.
   - `eval/push_recovery_eval.py`: added `--min_command_speed_mps` (floors
     each trial's sampled xy velocity-command magnitude, direction preserved
     when defined else a fixed random direction) and four new trial-CSV
     columns (`commanded_speed_mps`, `displacement_at_push_m`,
     `displacement_at_window_end_m`, `max_displacement_m`).
   - New script `play_training_progression.py`: one clip per periodic
     checkpoint, same terrain condition held fixed across every clip, to show
     gait-quality evolution across training (the "watch gait evolve across
     checkpoints" idea from `RUN_001.md`, never executed until now). Hit and
     fixed a real bug on first use — see "Process notes" below.
2. **Training**: fresh 1500-iteration Rough run from scratch (not resumed),
   same task/config as `RUN_001`'s stairs-rescale run, with the new
   diagnostic curriculum terms active.
3. **Eval**: a full magnitude sweep (0/40/80/120/160/200N x terrain levels
   0/4/8, 100 trials/cell) — the first time this project has run the *full*
   magnitude range against Rough (previous Rough sweeps used a narrower
   0/120N range built for the sub-terrain type comparison, not a curve).
4. **Video**: `play_training_progression.py` (11 clips, one per ~150-iteration
   checkpoint) and `eval/push_recovery_showcase.py` (29 clips, defaults).
5. **Checkpoint**: copied (not renamed — the original stays at its run-specific
   R2/local path) to `policy/locomotion/checkpoints/go2_locomotion_v1_candidate.pt`
   and synced to `r2://.../locomotion/checkpoints/go2_locomotion_v1_candidate.pt`,
   per `docs/project_structure.md`'s naming convention.

Runs were queued end-to-end via a small pipeline script (`nohup`+`disown`'d on
the pod, not dependent on any local session staying open) so the whole
sequence — train, video, eval, video, R2 sync after each step — executed
unattended.

## Results

### Training convergence

| iter | reward | terrain_levels (mean) | terrain_level_max | frac at max (9) | push k_c | base_contact |
|---|---|---|---|---|---|---|
| 0 | -0.46 | 3.53* | 6.0 | 0% | 0.30 | 0% |
| 166 | 10.08 | 0.43 | 7.67 | 0% | 0.48 | 12.3% |
| 499 | 18.01 | 3.20 | 9.0 | 0.6% | 0.76 | 7.0% |
| 832 | 17.12 | 5.53 | 9.0 | 11.1% | 0.91 | 11.9% |
| 1165 | 17.64 | 6.05 | 9.0 | 15.2% | 0.96 | 11.7% |
| 1499 (final) | 19.78 | 5.90 | 9.0 | 14.7% | 0.987 | 10.3% |

*(step-0 terrain_levels reading is a logging artifact from the first partial
batch, ignore it)*

`terrain_levels` (mean) and `frac_at_max` both climb steadily through
iteration ~1000, then hold in a tight, noisy band for the rest of training
(mean 5.9-6.05; frac_at_max peaks at 16.1% at iteration 1332, dips to 14.7% by
1499) rather than still trending upward — a real plateau, not a run cut short.
`base_contact` (fall rate) is flat at 10-12% since iteration ~666. Push
curriculum (`k_c`) is at 0.987, essentially saturated by its own asymptotic
design regardless of performance. Reward is noisier (dips to 17.1 mid-run,
recovers to 19.8 by the end) with no clear monotonic trend in the back half —
the one metric where a longer run *might* reveal a small residual
improvement, but nothing here resembles the still-climbing trajectory the
pre-stairs-fix run showed before its own (real) ceiling.

**Conclusion: this looks like genuine convergence for this network/reward/
hyperparameter configuration.** Training longer at the same settings would
likely reproduce similar numbers, not meaningfully improve them — unlike the
stairs-rescale fix, which was a real step-change unlock, simply extending
iterations is not expected to be a comparable lever. Per the handoff's own
scope ("don't hand-tune beyond the established recipe... this phase's value
is in getting the standard recipe running correctly"), a genuine further
improvement (bigger network, reward tuning) belongs to a later phase, not
more of the same training now.

### Eval-reliability fix — verification data

- **Command floor**: minimum commanded speed across all 1800 trials was
  exactly 0.5 m/s (the floor), zero trials below it — confirms the fix
  applied correctly.
- **Displacement — the flat-spawn-zone concern from `RUN_001.md`, settled**:
  **0.0% of trials, in every terrain type including `pyramid_stairs_inv`,
  showed max displacement under 1.0m.** Minimum displacement for
  `pyramid_stairs_inv` specifically was 1.73m, safely past its ~1.5m platform
  radius (confirmed geometrically in `RUN_001.md`). Mean displacement ranged
  9.3-12.3m across types. This directly confirms the command-floor fix
  eliminated the "free win" artifact — every trial's result now reflects
  genuine terrain interaction, including the previously-most-suspect
  `pyramid_stairs_inv` number.

### Video

`play_training_progression.py` (11 clips) and `push_recovery_showcase.py` (29
clips) both completed successfully. The training-progression script hit a
real bug on its first run: reusing `torch.inference_mode()` per-clip instead
of once for the whole loop caused a `RuntimeError: Inplace update to
inference tensor outside InferenceMode` on the second checkpoint's
`env.reset()` — fixed by wrapping the entire per-checkpoint loop (all resets
and steps) in one persistent `inference_mode` context, then re-run
successfully end to end.
